"What does dry-run mode do in stage1.py? Where does it send output?"
Dry-run mode prevents all real execution and filesystem writes. Here's exactly what it does:

How it works: main() sets the module-level _dry_run = True, which two helper functions check:

_run_command (stage1.py:29-31): skips subprocess.run entirely — no tool (cutadapt, STAR, featureCounts, etc.) is executed.
_makedirs (stage1.py:46-48): skips path.mkdir — no directories are created.
cleanup_intermediates (stage1.py:703-704): skips path.unlink — no files are deleted.
Where output goes: Everything goes to the Python logger (logger.info). Each skipped action is logged with a [DRY RUN] prefix, e.g.:


[DRY RUN] mkdir -p /scratch/.../cutadapt
[DRY RUN] cutadapt -g=^ATCG -e 0.15 ...
[DRY RUN] rm /scratch/.../STAR/sample_SJ.out.tab
The logger itself is not configured inside stage1.py — it uses the standard logging.getLogger(__name__) and relies on whatever logging setup the caller provides. When run directly via python stage1.py, no handler is configured, so by default log messages go nowhere unless the root logger has a handler set up. If you want to see the dry-run output when running directly, you'd add logging.basicConfig(level=logging.INFO) to the if __name__ == "__main__" block.

1. Is this specific to cutadapt?

No. Every tool that redirects output to a file had the same bug — cutadapt just happened to be first in the pipeline. FastQC, featureCounts, bam_stat.py, read_distribution.py, and MultiQC would all have crashed the same way on their turn.

2. Why didn't your bash script have this problem?

In bash, the > and 2> redirect operators are handled by the shell before the program starts. The shell opens the file and hands the program an already-open file descriptor. The program itself never sees a filename — just an open pipe.

In Python, calling subprocess.run() directly bypasses the shell entirely. Python doesn't interpret > — it just launches the program. So you become responsible for opening the file yourself and handing it in. That's what the fixed _run_command now does.

The complexity is deliberately isolated to _run_command. The domain functions (run_fastqc, trim_adapters, etc.) don't change — a student adding a new pipeline step just calls _run_command the same way every other step does:
